# Feature Worktree Fan-Out Validation

Run these scenarios against the primary opencode-server deployment before relying on feature fan-out in production:

1. Confirm the worktree plugin exposes `worktree_create` and `worktree_delete` inside the server session.
2. Restart the server and confirm worktree paths and `.git/worktrees` metadata survive.
3. Create `feature/<slug>` from `develop`, then create a child with `baseBranch=feature/<slug>`.
4. Confirm child sessions stream output to connected clients.
5. Confirm independent tickets share a manual batch while dependent tickets wait for merge and feature fast-forward.
6. Confirm sub-PRs use `feature/<slug>` as their exact base.
7. Disable the plugin and confirm exact manual worktree commands are printed and orchestration pauses.
8. Confirm `worktree_delete` refuses unmerged or unpushed work.
9. Confirm feature-mode code-review runs regression, integration, and e2e checks through the documented Docker/Sysbox path.
10. Introduce a sign-off defect and confirm it creates a new remediation ticket and child worktree rather than reopening a merged ticket.

## API-driven fan-out (added with `worktree-manager` + `plugins/worktree.js`)

These scenarios must pass after the worktree-manager subagent and the in-process plugin are deployed. They confirm that orchestration never bypasses the `/experimental/worktree` API and that the GUI stays in sync.

11. Confirm `agents/worktree-manager.md` exists, is registered in `opencode.json` under `agent.worktree-manager`, and is allowed by `agents/orchestrate.md` `task:` allow-list (`worktree-manager: allow`).
12. Confirm `plugins/worktree.js` is copied into `${OPENCODE_CONFIG_DIR}/plugins/` by the entrypoint, registers exactly four tools (`worktree_create`, `worktree_list`, `worktree_delete`, `worktree_reset`), and the opencode-server log shows `worktree plugin loaded` on boot.
13. From a fresh `orchestrate` session, dispatch a `worktree-manager` Task with `action: "create_feature"`, `slug: "<test>"`, `base: "develop"`. Expect the branch `opencode/feat-<test>` to appear in `git branch -a` inside the worktree directory and the worktree to appear in the Desktop GUI.
14. Dispatch `action: "create_ticket"`, `issue: <n>`, `slug: "<child>"`, `base: "opencode/feat-<test>"`. Expect `opencode/ticket-<n>-<child>` with `merge-base origin/opencode/feat-<test>` as an ancestor. Confirm the ticket branch is **not** `ticket/...` (the forbidden raw-git shape).
15. **API failure path:** stop the upstream `opencode serve` and dispatch any worktree action. Expect `worktree-manager` to return `blocker_code: WORKTREE_API_FAILED` with `manualRecovery` curl snippet. Expect the orchestrator to stop and **not** fall back to raw `git worktree` — no `git worktree add` lines should appear in any child transcript.
15a. **Dead upstream:** stop `opencode serve`, dispatch any worktree action. Expect `BLOCKED: WORKTREE_API_FAILED`, no `git worktree` fallback.
15b. **WorktreeNotGitError recovery:** simulate a context-less delete (or use the pre-fix plugin), dispatch `action: "delete"`. Expect `worktree-manager` to auto-recover via the sanctioned script + session deregister, returning `{ ok: true, recovered: true }`. Confirm the worktree is gone from `worktree_list`, `git worktree list`, and the GUI.
16. **Restart-reset path:** dispatch `action: "reset"`, `directory: "<ticket dir>"` after a simulated server restart. Confirm the worktree re-appears in the Desktop GUI session list within one poll cycle.
17. **Desktop UI smoke:** with one ticket worktree live, open the Desktop UI, confirm the worktree entry shows the session attached and the branch label renders `opencode/ticket-<n>-<child>` (not `ticket/<n>-<child>`).
18. **Self-guard on `OPENCODE_APPS_DIR`:** dispatch `action: "delete"`, `directory: "<anything under OPENCODE_APPS_DIR>"`. Expect `refused: PROTECTED_PROJECT_ROOT` from the plugin and the orchestrator to abort, not retry. Confirm no row was removed from `git worktree list` on the host.
19. **Hard-rule denial:** confirm `worktree-manager` cannot be invoked directly with `write: true` / `edit: true` (its frontmatter denies both) and that any bash attempt to run `rm -rf /`, `git push --force`, `git checkout -b <branch>`, or `git switch -c <branch>` is denied by its permission allow-list.
20. **One-shot contract:** confirm a single `worktree-manager` invocation handles exactly one action and that the orchestrator must re-dispatch for each lifecycle event (no batching inside the subagent).
21. **Recover action:** dispatch `action: "recover"`, `directory: "<stuck worktree dir>"` on an already-stuck worktree (one that failed a delete and still shows in `worktree_list`). Expect the sanctioned cleanup script (`rewrite-worktree-gitdirs.py remove/prune/scrub`) to run, orphan sessions to be deregistered via `DELETE /session/<id>`, and a re-list to confirm the worktree is gone from `worktree_list`, `git worktree list`, and the GUI.

## Develop loop: branch shape, auto-spawn, coder sessions

These scenarios confirm the develop-branch orchestrator and the coder-session ticket execution path. They run after the API-driven fan-out scenarios above and depend on them.

22. **Naming with `<abbrev>`.** Dry-run a feature with 5 tickets. Verify `git branch -r | grep opencode/` returns `feat-<slug>` + exactly 5 `ticket-<issue>-<slug>-<abbrev>` branches. Each `<abbrev>` is 3–6 kebab-case words derived from the issue title (lowercase, stopwords dropped, `-2/-3` appended only on collision). Confirm `<abbrev>` is **not** the full title and never contains slashes or uppercase.
23. **`auto_spawn` echo.** Dispatch `worktree-manager` `create_ticket` with `{ issue, slug, base, title, auto_spawn: true }`. Confirm the JSON response includes `auto_spawn: true` echoed back and `abbrev` set to the derived `<abbrev>`. Confirm the ticket branch matches `opencode/ticket-<issue>-<slug>-<abbrev>` exactly (no extra suffixes).
24. **Abbrev collision.** With two issues whose titles produce the same `<abbrev>`, dispatch two `create_ticket` calls. Expect the first to land on `opencode/ticket-<issue1>-<slug>-<abbrev>` and the second on `opencode/ticket-<issue2>-<slug>-<abbrev>-2`. Confirm `-3` on a third collision and `BLOCKED: WORKTREE_NAME_COLLISION` after `-9`.
25. **`scripts/dev-loop-batch.sh` DAG.** Pre-create 4 issues: A (no deps), B (no deps), C (Blocked by A), D (Blocked by B). Confirm the script returns A + B in one call, then C + D after their blockers close.
26. **Coder session runs the whole ticket (no orchestrator between stages).** With `auto_spawn_consent: true`, kick a 2-stage ticket to its coder session. Capture the coder session's transcript; confirm it dispatches one implementer Task per stage (test-writer RED → owner GREEN), **two** `code-review` calls (one per stage), opens the sub-PR, runs `scripts/pr-stabilize-watch.sh`, and emits exactly one `READY_FOR_HUMAN_REVIEW` or `BLOCKED` report. Confirm each implementer Task completes with its own report (the post-completion guard firing per Task is correct — each stage is a fresh Task), and that the coder session itself stops after the single terminal report.
27. **Silent per-ticket preflight happy path.** In a ticket worktree with valid `.env`/Infisical, the coder session runs `worktree-env` + `preflight` silently (delegated Tasks) and produces no user prompt. Confirm via the coder session's lifecycle log.
28. **Silent per-ticket preflight block path.** Force a preflight failure that survives one repair pass (e.g. missing `.env` copy after `worktree-env`). Coder session returns `BLOCKED: ENV_BLOCKED` with `recommended_env_fix`; develop orchestrator surfaces exactly one recommendation and pauses the batch — no auto-advance.
29. **PR stabilization in coder session.** With a CI failure on the sub-PR that can be fixed in-worktree (TDD), confirm the coder session's delegated implementer fixes, commits `Refs: #<n>`, pushes, and re-runs `scripts/pr-stabilize-watch.sh`. Loop bounded at 3 iterations; on exhaustion, confirm `BLOCKED: STABILIZATION_EXHAUSTED` is returned to the develop orchestrator.
30. **Cross-ticket review escalation.** Inject a review comment whose fix would touch files in a different ticket's branch. Confirm the coder session returns `BLOCKED: CROSS_TICKET_REVIEW`; the develop orchestrator surfaces it and waits for the user's "remediation" message. On "remediation", the develop orchestrator re-runs the final gates and re-kicks the feature coder's `remediation:` flow (`feature-review` §8).
31. **Single human gate.** With `auto_spawn_consent: true`, run a 3-ticket feature. Expect exactly 3 user notifications (one per sub-PR) and **zero** other prompts until the feature-architect session is started by the user.
32. **Remote-branch cleanup.** After each sub-PR merges, verify `git ls-remote origin` no longer lists `opencode/ticket-<issue>-<slug>-<abbrev>`. Orphan-remote-branch count = 0 mid-feature.
33. **Feature coder kickoff.** After all tickets merge into `opencode/feat-<slug>`, confirm the develop orchestrator dispatches `worktree-manager kickoff { directory: <feature worktree dir>, agent: coder, message: <pointer: feature slug, feat branch, "Load skill feature-review and begin"> }`. The feature coder session loads `feature-review`, runs §0 Bootstrap, full-suite `code-review`, one-shot CodeRabbit (medium/hard), difficulty gates, docs, `state:done`, feature PR, bounded stabilization, and posts one `feature_report:` comment on the PRD parent + best-effort `session_notify` back to the develop orchestrator. Confirm no `architect-feature-signoff` session is started by the user.
34. **Feature PR merge after "all reviewed".** After the feature coder's `feature_report: READY_FOR_HUMAN_REVIEW`, the develop orchestrator enforces the final gates (per-ticket `code_review_gate:` `all_stages: true` + `verified`; feature report APPROVED + full-suite evidence + CodeRabbit PASS + docs paths; all tickets `state:done`; `gh pr checks` green) and prints the merge prompt. On the user's "all reviewed" message, the develop orchestrator dispatches a `developer` Task (`load: minimal`, with explicit `cd <feature worktree dir>` + `git -C`) running `gh pr merge <pr_url> --squash --delete-branch=false`. Then close-loop: delegated `developer` runs `git push origin --delete opencode/feat-<slug>`; `worktree-manager delete { directory: <feature worktree dir> }` succeeds; delegated `developer` (in main checkout) runs `git fetch && git pull --ff-only origin develop`. Print `feature:<slug> complete in <OWNER/REPO>; ready for spec feature-complete`.
35. **Worktree + remote-branch ownership.** Confirm no coder-session transcript contains `git push origin --delete` or any `worktree_*` tool call. Confirm the develop orchestrator never runs `git push origin --delete` itself — it always delegates to a `developer` Task with `load: minimal`.
36. **Skill allowlist.** Confirm `agents/orchestrate.md` `skill:` allow object includes only `orchestrate`, and `agents/coder.md` includes `ticket-lifecycle` + `feature-review`. Removing any of them causes a `SKILL_UNAVAILABLE` failure at load time. Confirm `orchestrate-sandbox` is no longer in any agent's skill allow-list.

## Coder-session kickoff reliability

Ticket work is never dispatched via the `task` tool — subagents inherit the develop orchestrator's cwd (`develop`) and `scripts/checkout-contract.sh --verify` rejects them. The auto-started GUI session for the ticket worktree IS the coder session; it self-bootstraps from `<worktree-gitdir>/opencode-ticket-brief.json` and reconstructs the rest from GitHub. These scenarios run after the develop-loop scenarios above and depend on them.

37. **`create_ticket` with kickoff.** From the develop orchestrator, dispatch `worktree-manager create_ticket { issue, slug, base, title, auto_spawn: true, kickoff_agent: "coder", kickoff_message: <short pointer from §5a> }`. Expect: HTTP 200 from `/experimental/worktree`, `<worktree-gitdir>/opencode-ticket-brief.json` exists on disk, `gitdir` resolved via `<worktree>/.git` (a file containing `gitdir: <path>`), the file is NOT visible in `git status` inside the worktree, the plugin polls `session.list` and finds the auto-started GUI session within 15s, `session.promptAsync` returns 204, the response envelope includes `kickoff: "admitted"`, `session_id`, `develop_session_id`, `brief_file`. Open the GUI session in the Desktop UI; confirm the kickoff message is the first user message visible there and the session's agent is `coder`.
38. **Kickoff race → retry.** Run a `create_ticket` with `kickoff_message` against a freshly-restarted opencode-server (session auto-start is still warming up). Expect `kickoff: "no_session_after_poll"` and an advisory `blocker_code: "KICKOFF_FAILED"`. The brief file is durable. Dispatch `worktree-manager kickoff { directory, agent, message }` (same short pointer). Expect `kickoff: "admitted"` on retry — the brief file is reused, the plugin overwrites it deterministically.
39. **Garbage/missing brief file reconstruction.** With a valid ticket worktree (correct branch, correct base), delete `<gitdir>/opencode-ticket-brief.json` (simulating crash/restart recovery). Confirm the coder session's `ticket-lifecycle` §0 Bootstrap reconstructs from GitHub: branch shape `opencode/ticket-(\d+)-<slug>-(.+)` → issue number, `gh repo view` → repo, `gh issue view <n> --json body` → `opencode-task-yaml`, `feature:<slug>` label → feature slug. Confirm the ticket proceeds to stage 1 without ever asking the user to paste a brief.
40. **Duplicate kickoff → resume, not restart.** Inject a duplicate kickoff message (second `session.promptAsync` with the same pointer) into a coder session that has already passed stage 1. Confirm the coder session does not re-run RED/GREEN for already-approved stages — it reads the most recent `code_review_gate:` comment to find `last_approved_stage_index` and advances from `index+1`. Confirm no duplicate `code_review_gate:` comments are posted.
41. **Terminal report wakes develop orchestrator.** Complete a ticket end-to-end. Expect the coder session to post a `ticket_report:` comment on the issue (status: `READY_FOR_HUMAN_REVIEW`, pr_url, ci_state, stages_completed, next_action) AND best-effort `session_notify` (called by the coder itself) to `develop_session_id` (from the brief file). Confirm the develop orchestrator receives an injected message beginning with `ticket_report:` and runs the PR-approval gate (single user prompt). After user approval reply, confirm the develop orchestrator merges the sub-PR (delegated `developer` Task with explicit `cd`/`git -C`), fast-forwards `opencode/feat-<slug>`, deletes the ticket worktree via `worktree-manager`, and deletes the remote ticket branch. Confirm the next batch is kicked without further user paste.
42. **Out-of-band GitHub-UI merge.** With the poller running, user merges a sub-PR via the GitHub UI (not via the develop orchestrator's gate). Confirm the poller's next tick detects the PR state change via `gh pr view --json state`, computes a `DEV_LOOP_WAKE { repo, feature, reason: "ticket_report delta" }`, `promptAsync`s the develop orchestrator session with `agent: orchestrate`. Confirm the develop orchestrator runs `scripts/dev-loop-watch.sh`, sees the merged PR, verifies via `gh pr view`, and proceeds to cleanup + re-batch. No user intervention needed. If the poller is disabled, confirm `scripts/dev-loop-watch.sh` is still agent-invocable and the user can manually trigger the same wake.
43. **`auto_spawn_consent: false` (no injection).** With consent declined, dispatch `worktree-manager create_ticket` **without** `kickoff_message`. Expect the worktree to be created, NO `<gitdir>/opencode-ticket-brief.json` to be written, NO promptAsync to be sent, and the response envelope to match the plain `create_ticket` shape (no `kickoff` field). Confirm the GUI session is idle; when the user switches the session's agent to `coder` and types "begin", confirm the coder session's `ticket-lifecycle` §0 Bootstrap reconstructs from GitHub (issue number from branch, `gh repo view`, `gh issue view --json body`) and proceeds.
44. **Contract compliance.** Confirm no coder-session transcript contains `worktree_*` tool calls or `git push origin --delete`. Confirm the develop orchestrator never dispatches ticket work via the `task` tool (subagent cwd inheritance would land on `develop`). Confirm `<worktree-gitdir>/opencode-ticket-brief.json` never appears in `git status` inside the worktree (the file is in the gitdir, not the working tree). Confirm `scripts/validate-opencode-config.sh` passes after the deployment — specifically the `session_notify` + `session.promptAsync` + `opencode-ticket-brief.json` assertions in `plugins/worktree.js`, the `kickoff` action + `KICKOFF_FAILED` advisory in `agents/worktree-manager.md`, the `ticket_report:` marker + Bootstrap language in `skills/ticket-lifecycle/SKILL.md`, and `scripts/dev-loop-watch.sh` + `scripts/dev-loop-poller.sh` executability.

## Feature coder + final-gate loop (added with `feature-review`)

These scenarios confirm the feature coder's `feature-review` loop and the develop orchestrator's final-gate + merge gate. They run after the orchestrator/coder split scenarios and depend on them.

58. **Feature coder loop end-to-end (no architect session involved).** From the feature worktree at `opencode/feat-<slug>` after every ticket sub-PR merged, the feature coder loads `feature-review` and runs §0 Bootstrap (pointer + branch + GitHub reconstruction; checkout contract verified), full-suite `code-review` via the compose backend (full diff vs `develop` + rolled-up acceptance mapping), one-shot CodeRabbit (medium/hard ⇒ `PASS`; easy ⇒ `SKIPPED`), difficulty gate (easy ⇒ none; medium ⇒ `review` completion summary; hard ⇒ `senior-dev scheduled_review`), `document` + `scribe` for docs (changelog required; guides/architecture per scope) committed on the feat branch before the PR opens, `state:done` on every `feature:<slug>` issue via `scripts/issue-state-transition.sh` (issues stay open), `scripts/feature-finish-pr.sh <slug>` opens the feature PR, bounded stabilization loop (max 3 iterations; after any fix, full-suite `code-review` re-runs), and one terminal `feature_report:` comment posted on the PRD parent issue + best-effort `session_notify` to `develop_session_id`. Confirm zero `architect-feature-signoff`/`architect-review`/Mode F references in the transcript; confirm no `HANDOFF_TO_FEATURE_ARCHITECT` JSON emitted.

59. **Orchestrator final gates + "all reviewed" → merge + close-loop + spec handoff.** After the feature coder's `READY_FOR_HUMAN_REVIEW`, the develop orchestrator runs the final gates (per-ticket `code_review_gate:` `all_stages: true` + `verified`; feature report APPROVED + full-suite evidence + CodeRabbit PASS + docs paths; all tickets `state:done`; `gh pr checks` green; branch policy intact — each via delegated `developer` where shell is needed), prints the merge prompt exactly: `Feature <slug> ready for final review: <pr_url>` plus the "all reviewed" instruction, waits for the user's reply, and on "all reviewed" dispatches a `developer` Task with explicit `cd <feature worktree dir>` running `gh pr merge <pr_url> --squash --delete-branch=false`. Then close-loop: delegated `developer` runs `git push origin --delete opencode/feat-<slug>`; `worktree-manager delete { directory: <feature worktree dir> }` succeeds; delegated `developer` (in main checkout) runs `git fetch && git pull --ff-only origin develop`. Emits exactly one of: `feature:<slug> complete in <OWNER/REPO>; ready for spec feature-complete` or `feature:<slug> complete in <OWNER/REPO>; ready for next feature`. No `HANDOFF_TO_FEATURE_ARCHITECT` JSON; no Mode F / Phase R language.

60. **Remediation.** When `feature-review` surfaces unmet acceptance or cross-ticket findings, the feature coder dispatches `to-tickets` (`load: full`) via `developer` to publish one or more `remediation:` GitHub issues in the impl repo, each linked as a sub-issue of the PRD parent (`--parent-issue <prd_parent_issue_url>` from `docs/prd/<slug>.md` frontmatter), with `design_delivery` and `stages[]` in the body, and returns `BLOCKED: FEATURE_REMEDIATION` with the issue numbers. The develop orchestrator surfaces it and waits for the user's "remediation" message; on "remediation", re-runs the final gates and re-kicks the feature coder (or, if the remediation issues need new ticket worktrees, dispatches them through the normal ticket pipeline via `worktree-manager create_ticket`).
